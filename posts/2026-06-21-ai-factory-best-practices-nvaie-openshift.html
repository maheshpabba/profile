"AI-Factory Best Practices: Deploying NVIDIA AI Enterprise on Bare-Metal OpenShift"

Mahesh Pabba 2026-06-21 All posts

Every NVIDIA AI Enterprise (NVAIE) deployment on OpenShift follows roughly the same sequence — and almost nobody writes it down in one place. The official docs cover each operator in isolation; the gaps between them (which order to install things in, which node labels gate which component, what a driver-load race actually looks like in practice) get relearned by every team that builds one of these clusters.

I turned the sequence I use into a public reference: maheshpabba/AI-Factory-Best-Practices. It mirrors an internal AI-Factory build document section by section, with every section linking to the actual manifests, scripts, and test artifacts that implement it — not just prose.

This post walks through the architecture decisions behind it.

Three Networks, Not One

A GPU worker node in this design carries three logically separate network planes:

  • Frontend / primary CNI — the OpenShift SDN plane, used for node management and general cluster traffic.
  • East/West compute (scale-out) RDMA fabric — the high-speed interconnect NCCL collectives run across, node to node.
  • Storage / backend fabric — isolated from compute traffic so a saturated training job doesn't starve storage I/O, or vice versa.

Getting this right starts before the cluster exists. Before you ever open the Assisted Installer, you need every node's hostname, MAC address, static IP/subnet/gateway, plus cluster DNS/NTP/VIPs — captured in a table, then converted into NMState YAML so the install is unattended and repeatable instead of a sequence of manual web-console clicks per node.

Doing this by hand for more than a handful of nodes is where mistakes creep in — a transposed MAC address, a wrong VLAN — so the repo includes Scripts/cluster-utility.sh and its PowerShell twin, cluster-utility.ps1. They discover nodes by name or role, print RDMA device/PCIe/interface tables filtered by adapter family (ConnectX-7, ConnectX-8, BlueField), and generate NodeNetworkConfigurationPolicy (NNCP) YAML directly from what they find on the hardware — rather than from a spreadsheet that can drift out of sync with reality.

NMState: Declarative Network State, Reconciled Continuously

Once the cluster exists, the NMState Operator takes over ongoing network configuration. The model is simple but easy to get backwards the first time:

  • NNCP (NodeNetworkConfigurationPolicy) — the desired state you declare: interfaces, MTU, VLANs, for one or more nodes.
  • NNS (NodeNetworkState) — the read-only current state NMState reports back, per node.

You write NNCPs; NMState reconciles live interfaces toward them and reports NNS back so you can verify convergence. The nmstate/ directory in the repo holds the actual nncp-*.yaml and nns-*.yaml objects used on this cluster's workers — generated by the same cluster-utility script and applied with a plain oc apply -f.

A Dedicated MachineConfigPool for GPU Nodes

GPU worker nodes need kernel-level changes that the rest of the cluster should never see:

  • Blacklist the inbox irdma / rpcrdma kernel modules — they conflict with the NVIDIA/Mellanox MOFED driver stack.
  • Disable IOMMU.
  • Configure huge pages.

Apply these cluster-wide and every node reboots to pick them up, including nodes that will never touch a GPU. The fix is a dedicated MachineConfigPool — Misc/custom-role-gpuworker.yaml — scoped to a custom gpu-worker role, so only the nodes that opted into that role ever reboot for these changes.

The Operator Stack — and the Race Condition Between Two of Them

NVIDIA AI Enterprise on OpenShift is really four operators working together:

Component Responsibility
Node Feature Discovery Labels nodes with detected PCI/GPU/NIC hardware so the operators below can target the right ones
NVIDIA Maintenance Operator Coordinates cordon/drain for firmware updates and driver reloads
NVIDIA Network Operator Provisions MOFED/DOCA-OFED, the RDMA device plugin, and NIC QoS/VLAN configuration
NVIDIA GPU Operator Provisions the GPU driver, container toolkit, device plugin, and DCGM monitoring

The Network Operator and the GPU Operator both load kernel modules on the same nodes — and if they do it at the same time, you get a race condition that manifests as intermittent driver load failures that are maddening to debug after the fact, because the symptom shows up on a random subset of nodes on a random day.

The fix lives in how the GPU Operator is configured. Rather than letting ClusterPolicy manage the GPU driver directly, the repo splits driver management out:

  • ClusterPolicy configures every GPU Operator component except the driver (driver.enabled: false, driver.useNvidiaDriverCRD: true) — see GPU-Operator/gpu-cluster-policy.yaml.
  • A separate NVIDIADriver object, per node (GPU-Operator/gpu-driver.yaml), supplies the driver itself — gated on the Network Operator's network.nvidia.com/operator.mofed.wait node label.

The GPU driver simply doesn't load until the Network Operator has finished its own kernel module work and cleared that label. Two operators, one shared resource, one explicit ordering gate instead of a hope that timing works out.

On the networking side, NicClusterPolicy handles the cluster-wide singleton components (DOCA telemetry, the NIC Configuration Operator), NicNodePolicy handles the per-node DOCA-OFED driver and RDMA shared device plugin selected by hostname, and NicConfigurationTemplate tunes RoCEv2 QoS — PFC, ECN, trust mode — separately for the backend/compute fabric and the storage fabric.

Testing: Two Independent Paths to the Same Answer

A cluster that installs cleanly and a cluster that's actually ready for distributed training are two different claims. The repo validates the fabric two ways, deliberately kept independent of each other:

  1. Hand-written Kubeflow MPIJob / TrainJob manifests — full control over NCCL environment variables and privileged pods, used as an independent baseline that doesn't depend on any NVIDIA tooling being correctly configured.
  2. NVIDIA's nvcrectl Cluster Readiness Engine — WorkloadRun / Certification CRDs, producing NVIDIA's standard certification report format.

Both paths exercise the same NCCL collectives — AllGather, AllReduce, AllToAll, ReduceScatter — plus a short Nemotron5 Megatron-LM training smoke test, and a continuous RDMA QoS/PFC fairness test under sustained load. If the hand-written path and the vendor-tooling path agree, you've validated both the fabric and the tooling. If they disagree, you've found a bug before a researcher does.

Running nvcrectl workloads requires a mutating admission webhook for the privileged/macvlan access the test pods need — the same cluster-utility.sh script handles that too, via -T prepare/status/cleanup, documented in Scripts/cluster-utility.md.

Publishing Infrastructure Docs Without Leaking Infrastructure

The one piece of this repo that isn't a manifest or a script is a policy: what gets published and what doesn't.

The repository runs two branches on purpose. Dev is the working collection — environment-specific examples, real node names, real addresses, in-progress scripts. main contains only material that's been explicitly reviewed and approved for public visibility. Nothing gets merged or cherry-picked from Dev into main; publishing means building a clean snapshot of specific files on top of main, reviewing the staged diff, and committing that — every time, not as a one-off.

It sounds like overhead until you remember that this is a public GitHub repository, and that deleting a file later does not remove it from Git history. The appendix is the clearest example: the source document includes an example leaf switch configuration with live BGP peer passwords and admin SSH keys. The equivalent file here — switch-configs/switch-config.txt — is .gitignore'd and has never been committed to either branch. Sanitizing a file before its first commit is the only sanitization that actually works; everything after that is incident response.

Why This Exists as a Repo and Not Just a Doc

Most of what makes an AI-Factory build succeed or fail isn't a single setting — it's the ordering: NMState before cluster creation, the GPU role's MachineConfigPool before the operators land, the Network Operator's MOFED label before the GPU driver loads, both test paths before anyone trains on the cluster. Writing that down as prose gets stale the moment a manifest changes. Writing it down as a README that links directly to the manifests, scripts, and test results it describes means the documentation and the implementation can't drift apart without someone noticing.

That's the whole premise of AI-Factory-Best-Practices: a build sequence you can read top to bottom, and a repo you can oc apply -f against, kept in the same place.
